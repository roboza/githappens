# Performance benchmarks

Spec 15 §7 ("Perf" and "Visual" rows), spec 02 §6.15 / §6.16 / §9 and spec 04 §7 step 26 / §9.
Three opt-in suites; none of them runs in the normal `pnpm test` / `test:e2e` jobs.

| Suite                 | Command                                                                                             | Strict mode        |
| --------------------- | --------------------------------------------------------------------------------------------------- | ------------------ |
| Git engine benchmarks | `pnpm bench`                                                                                        | `BENCH_STRICT=1`   |
| Graph / renderer perf | `GH_PERF=1 pnpm --filter @githappens/desktop exec playwright test e2e/perf.spec.ts --workers=1`     | `GH_PERF_STRICT=1` |
| Visual regression     | `GH_VISUAL=1 pnpm --filter @githappens/desktop exec playwright test e2e/visual.spec.ts --workers=1` | always strict      |

Without the strict variable a missed threshold is printed as `!!` and the run still succeeds, so slow
dev machines don't fail. The nightly workflow `.github/workflows/perf.yml` runs the first two in strict
mode on ubuntu-latest and uploads `bench-results/*.json` and `apps/desktop/test-results/`.

## Fixtures

Generated by `test/fixtures/src/perf.ts` with one streamed `git fast-import` each (no git process per
commit; fixed dates, authors and a seeded PRNG, so SHAs are identical everywhere):

| Fixture       | Default size                                                                          | Small variant (unit tests)                  |
| ------------- | ------------------------------------------------------------------------------------- | ------------------------------------------- |
| `huge`        | 200k commits, up to 8 concurrent topic branches merged `--no-ff`, commit-graph        | `--count=600 --lanes=6 --commitGraph=false` |
| `huge-1m`     | 1M commits, 16 lanes (bench only)                                                     | `--count=…`                                 |
| `files-100k`  | 100k tracked files in 100-file directories                                            | `--files=1234`                              |
| `branches-5k` | 5k local branches tracking 5k `origin/*` branches (±3 commits), 100 tags, packed-refs | `--branches=50 --commits=40 --tags=5`       |

`pnpm fixtures` skips these four; build one explicitly with
`pnpm fixtures huge --root=<dir>` (options are passed through, e.g. `--count=1000000`).

`pnpm bench` and the perf e2e share a cache in `test/fixtures/.repos/bench` (gitignored; override with an
absolute `GH_BENCH_CACHE`). The bench stamps each fixture with a hash of the generator sources, its
options and the git version, and regenerates when any of them changes. First build on a 2019 6-core
Windows desktop: `huge` ≈ 45 s, `huge-1m` ≈ 3.5 min, `files-100k` ≈ 40–90 s, `branches-5k` ≈ 2 s.

## `pnpm bench` (packages/git/bench/run.ts)

Uses the real `GitService`, `OperationQueue` and `GitProcessRunner` with the git the app ships
(dugite's portable git, with its own system config; falls back to git on PATH, or `GH_BENCH_GIT`).
The user's global config is replaced with an empty file.

```
pnpm bench                     # all suites
pnpm bench --quick             # skip the 1M repo and the graph layout bench
pnpm bench --only=log,status   # suites: log, million, status, refs, graph
pnpm bench --out=results.json  # default bench-results/git-bench.json
pnpm bench --huge-count=50000 --files=20000 --branches=1000   # smaller fixtures
```

## Graph / renderer perf e2e (apps/desktop/e2e/perf.spec.ts)

Runs against the built app (`npx electron-vite build` in apps/desktop first) on `huge`, and on `huge-1m`
when it exists in the cache (or with `GH_PERF_1M=1`).

| Measurement                                                                                                   | Threshold           | Source                  |
| ------------------------------------------------------------------------------------------------------------- | ------------------- | ----------------------- |
| First graph rows, renderer time since navigation (200k and 1M)                                                | 2000 ms             | spec 15 §7              |
| Fling scroll (4000 px/frame through 200k loaded rows): main-thread work per frame, p95, from a Chromium trace | 16 ms (8 ms logged) | spec 15 §7 (spec 04 §9) |
| Frames with blank rows (fling and wheel speed)                                                                | 0 (always enforced) | spec 04 §9              |
| Renderer JS heap with 200k rows loaded                                                                        | 400 MB              | spec 04 §7 step 26      |
| External save → WIP row, p95 of 10                                                                            | 500 ms              | spec 02 §9              |

It also logs the launch → first-rows time, renderer boot milestones, the app's own git command log up
to the first rows (`git:output:list`) and the load-all time. Results go to
`bench-results/perf-e2e.json`; `GH_PERF_TRACE=1` additionally writes the scroll traces
(`apps/desktop/test-results/perf-*-trace.json`, open in https://ui.perfetto.dev).

## Visual regression (apps/desktop/e2e/visual.spec.ts)

The `branchy` fixture in the light and dark themes (set through `settings:set`, like Preferences),
ISO dates in UTC, initials instead of avatars, 1280×800 window, `toHaveScreenshot` with
`maxDiffPixelRatio: 0.01`. Baselines are per platform (`e2e/visual.spec.ts-snapshots/graph-*-win32.png`
are in the repo); create others with `--update-snapshots` on that OS.

## Notes from the first runs (Windows 11, Ryzen 5 3600, loaded machine)

- Process spawn dominates small git calls on Windows (≈ 100–150 ms per `git` under load).
- `--date-order` is not a streaming fallback without a commit-graph: like `--topo-order` it walks the
  whole history first (≈ 1.3–2 s on 200k commits). Only the default order streams.
- `%(upstream:track)` costs ≈ 1.5–3 ms per tracked branch (≈ 7–15 s for 5k), with or without a
  commit-graph; `--count` / `--sort` don't help (every ref is formatted before sorting).
- `GIT_CONFIG_NOSYSTEM=1` disables Git for Windows' `core.fscache` and makes status ≈ 10× slower; the
  bench therefore keeps the bundled git's system config, as the app does.
- `--untracked-files=all` can't use the untracked cache and with fsmonitor is slower than without
  (files-100k: ≈ 300 ms vs ≈ 175 ms; `--untracked-files=normal` with a written cache ≈ 100–140 ms).
- `@parcel/watcher` without an explicit `backend` probes for watchman on every `subscribe` through a
  synchronous popen (`cmd /c watchman …`): 0.35–0.4 s of blocked main process per subscribe when idle,
  seconds under load, three subscribes per repo open.

## What the app does about it (Phase 10 perf pass)

| Problem                                      | Fix                                                                                                                                                                                                                         | Before → after (bench / e2e, this machine) |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Repo open blocked by the watcher             | `RepoWatcher` names the native backend (`windows` / `fs-events` / `inotify`); `RepoManager.open` no longer awaits `start()` and queues one `status` refresh once it is armed                                                | subscribe ≈ 370 ms → < 5 ms each           |
| 5k-branch ahead/behind                       | `refs()` computes track itself only up to 50 tracking branches; above, HEAD + the 20 newest now, the rest in one background `for-each-ref` (`upstream.trackPending`), cached per (tip, upstream tip), then a `refs` refresh | 6.9 s → 0.48 s first call, 0.25 s cached   |
| First graph page: `rev-parse` + `stash list` | HEAD / stash tips read from `.git/HEAD`, `packed-refs` and the stash reflog (spawn fallback for reftable / odd symrefs)                                                                                                     | first 500 (commit-graph) 181 → 87 ms       |
| No commit-graph: ordered walk buffers        | seeded first page: a streaming default-order `--max-count=500` probe, reordered children-first, while the ordered walk runs; the walk then continues without the seeded commits                                             | first page 1.49 s → 0.12 s                 |
| Index caches never written                   | background `index.refresh` op (locking status) through the queue, ≤ once per 5 min, when `core.fsmonitor` / `core.untrackedCache` are on; status uses `-unormal` + expands untracked dirs                                   | fsmonitor status 292 → 102 ms              |
| Save → WIP row                               | watcher debounce gets a leading edge (first event after quiet is emitted at once; trailing / max-wait / flood unchanged)                                                                                                    | see perf e2e                               |

## Phase 11 follow-ups

| Problem                                                   | Fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Before → after (this machine)                                                                                            |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 5k-branch ahead/behind arrives all at once                | background pass in chunks (first 100 refs, growing to 500; 2 calls in flight at background priority), HEAD's branch / `prioritizeTrack()` hints first, then most recently committed; `onTrackUpdated` at most every 400 ms; refs() leaves pairs the running pass will count to it; a pass restarts (fresh tips, cached pairs skipped) only when refs moved                                                                                                                                              | all badges after 6.3 s in one go → first chunk 0.8–0.9 s after the call (0.35–0.45 s after it returned), all ≈ 5.9–6.3 s |
| Second graph page without commit-graph waits for the walk | windowed paging (`StreamingLogCursor`): each page is `git log --topo-order F --not F'` over a frontier F, drawn from one streaming default-order walk (S) — a window closed under descendants, so pages stay topologically consistent also with clock skew; a lookahead guard drops commits that are parents of anything still to come; the full ordered walk starts after the first window and takes over once it prints; a commit-graph written meanwhile turns the rest into one streaming walk of F | next 2000: 1077 → 115–165 ms; first page 113 → 165–250 ms (one more spawn, the window walk)                              |
| Commit-graph write not cancellable                        | `maintenance.commitGraph` op (queue class `maintenance`: runs beside user ops, never two at once, no watcher mute / refresh, not `busy`); status-bar Cancel; a killed write's `commit-graph.lock` / `tmp_graph_*` are removed                                                                                                                                                                                                                                                                           | —                                                                                                                        |
| Delete right after a save waits for the 300 ms window     | leading-edge debounce allows up to 4 follow-up events per burst to be emitted at once; the renderer re-runs an in-flight status once (dirty flag) instead of stacking                                                                                                                                                                                                                                                                                                                                   | see perf e2e (delete p95)                                                                                                |
